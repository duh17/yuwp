## Goal
Compare Qwen3-ASR-0.6B vs 1.7B for local streaming dictation on Apple Silicon.
Determine if the smaller model is good enough for streaming partials (with 1.7B
batch correction on stop).

## Models to test
| Model | Format | Weight Memory | Peak Inference |
|-------|--------|--------------|----------------|
| Qwen3-ASR-1.7B-bf16 | mlx-audio (current) | ~8GB | ~8GB |
| Qwen3-ASR-0.6B-4bit | MLX (speech-swift) | 675MB | ~2.2GB |
| Qwen3-ASR-0.6B-8bit | MLX | 1.0GB | ~2.5GB |
| Qwen3-ASR-0.6B CoreML INT8 | CoreML (ANE) | 180MB | ~400MB |

## Metrics to capture per model
- **Latency**: ms per 2s chunk (streaming), ms per full audio (batch)
- **Accuracy**: WER or manual quality check on test recordings
- **Memory**: RSS, MLX unified memory, peak during inference
- **CPU/GPU**: utilization during streaming vs batch
- **Language**: English, Chinese, mixed — quality per language

## Test data
- Saved recordings in `~/Library/Application Support/Yuwp/recordings/`
- Use the sidecar HTTP API for consistent measurement
- Feed same recordings to each model, compare outputs

## Experiment design
1. Start sidecar with model A on port 9748
2. Run benchmark script: feed recordings, collect partials + final + timing
3. Kill sidecar, start with model B, repeat
4. Compare results side-by-side

## Qwen Official Streaming Protocol (DashScope Realtime API)

Ref: https://www.alibabacloud.com/help/zh/model-studio/qwen-asr-realtime-interaction-process

WebSocket sequence diagram extracted from their docs:

```
Session Init:
  Client → Server: 客户端建立连接 (WebSocket connect)
  Server → Client: session.created

Update (optional):
  Client → Server: session.update
  Server → Client: session.updated

Audio Loop [多轮交互]:
  Client → Server: input_audio_buffer.append  (repeated, streaming PCM)
  Server → Client: input_audio_buffer.speech_started
  Server → Client: conversation.item.created
  Server → Client: conversation.item.input_audio_transcription.text  (streaming partials!)
  Server → Client: conversation.item.input_audio_transcription.text
  Client → Server: input_audio_buffer.append  (continues)
  Server → Client: conversation.item.input_audio_transcription.text

Stop:
  Client → Server: session.finish
  Server → Client: input_audio_buffer.speech_stopped
  Server → Client: commit audio buffer (internal)
  Server → Client: input_audio_buffer.committed
  Server → Client: conversation.item.input_audio_transcription.text
  Server → Client: conversation.item.input_audio_transcription.text
  Server → Client: conversation.item.input_audio_transcription.completed
  Server → Client: session.finished
  Client → Server: disconnect
```

Key observations:
- Uses WebSocket, not REST — persistent bidirectional connection
- Audio sent as `input_audio_buffer.append` (can be raw PCM or base64)
- Server-side VAD: `speech_started` / `speech_stopped` events
- Streaming partials via `conversation.item.input_audio_transcription.text`
- Final committed transcript on `transcription.completed`
- Multi-turn: audio buffer can be committed multiple times in one session

This could become a third SttProvider:
- `DashScopeSttProvider` — cloud-based, WebSocket, lowest latency for long sessions
- Compare against local 0.6B and 1.7B
- Needs DashScope API key (free tier available)
